## Tech stack

| Layer | Choice |
|---|---|
| Framework | Next.js 16, App Router, TypeScript strict mode |
| Styling | Tailwind CSS v4 + shadcn/ui (new-york style) |
| Database | Supabase Postgres via Drizzle ORM (postgres-js driver) |

## Folder structure

```
app/                    Routes, layouts, pages, loading.tsx, error.tsx
  (auth)/               Route group for unauthenticated pages
  (dashboard)/          Route group for authenticated pages
components/             Shared UI components
  ui/                   shadcn/ui primitives (generated by CLI — do not hand-edit)
hooks/                  Custom React hooks
lib/                    ALL server-side logic lives here
  db/                   Drizzle client + schema
    schema/             One file per domain (users.ts, posts.ts, …)
    migrations/         .md docs per migration; generated SQL goes in migrations/sql/
  supabase/             Three separate Supabase client modules (see below)
  r2.ts                 Cloudflare R2 helpers (optional — unused until R2 is wired)
  env.ts                Zod-validated env — import `env` from here, never process.env
  utils.ts              cn() helper used by all shadcn components
types/                  Shared TypeScript types
  supabase.ts           Auto-generated by `supabase gen types typescript` — do not hand-edit
  index.ts              Barrel re-export + hand-written shared interfaces
public/                 Static assets
```

## Hard rules

1. **All database queries live in `/lib`.** Never write a Drizzle query inline inside a component, page, or route handler. Route handlers and Server Actions call a `lib/` function that returns typed data.

2. **Every migration gets a `.md` file** in `lib/db/migrations/` explaining what changed and why. The generated SQL goes in `lib/db/migrations/sql/` (gitignored). Run SQL manually in the Supabase SQL Editor or via psql.

3. **`lib/env.ts` is the only place to read env vars.** Import `env` from `@/lib/env` everywhere else. Never read `process.env` directly outside that file (except the two `NEXT_PUBLIC_*` vars in `lib/supabase/server.ts` and `lib/supabase/client.ts`, which must be available before the env module loads).

4. **Three Supabase clients — use the right one:**
   - `lib/supabase/server.ts` — Server Components, Route Handlers, Server Actions. Uses anon key + RLS. Always `await createSupabaseServerClient()`.
   - `lib/supabase/client.ts` — Client Components only. Factory function; memoize it with `useMemo` or a context.
   - `lib/supabase/admin.ts` — Singleton `supabaseAdmin`. Bypasses RLS entirely. Only in server-side code you control (never reachable from the browser bundle).

5. **`components/ui/` is owned by the shadcn CLI.** Run `npx shadcn@latest add <component>` to add primitives. Don't hand-edit generated files there — put customizations in wrapper components in `components/`.

## Design system

For **general frontend-design principles** (color theory, accessibility, layout patterns, when to use which component anatomy) lean on the `frontend-design` plugin from `claude-plugins-official`. This section only covers what's **specific to this codebase** — the choices we've made that override or specialize the defaults.

### Tailwind v4

This project uses Tailwind CSS v4. The key differences from v3:

- **No `tailwind.config.js`.** All theme configuration lives in `app/globals.css` inside an `@theme {}` block.
- **PostCSS plugin is `@tailwindcss/postcss`**, not `tailwindcss`. See `postcss.config.mjs`.
- **Animation utilities** come from `tw-animate-css` (imported in `globals.css`), not `tailwindcss-animate`.
- Tailwind utilities reference CSS custom properties, not hardcoded values. Prefer semantic tokens (`bg-background`, `text-foreground`, `text-muted-foreground`) over raw color utilities (`bg-white`, `text-gray-900`).

### Color tokens

All color tokens are defined as `oklch()` values in `app/globals.css`. Dark mode is class-based (`.dark` on `<html>`). Use only the semantic token names — never hardcode colors.

| Token | Use for |
|---|---|
| `background` / `foreground` | Page background and primary text |
| `muted` / `muted-foreground` | Subtle backgrounds, secondary text |
| `card` / `card-foreground` | Card surfaces |
| `primary` / `primary-foreground` | Primary actions, CTAs |
| `secondary` / `secondary-foreground` | Secondary actions |
| `accent` / `accent-foreground` | Hover states, highlights |
| `destructive` | Delete / danger actions |
| `border` | Borders and dividers |
| `input` | Form input borders |
| `ring` | Focus rings |

### Typography

Fonts are loaded via the `geist` npm package, not `next/font`. They inject CSS custom properties (`--font-geist-sans`, `--font-geist-mono`) via `.variable` classes on `<body>`, which the `@theme` block maps to `--font-sans` and `--font-mono`.

- Use `font-sans` for all UI text (resolves to GeistSans).
- Use `font-mono` for code, IDs, timestamps (resolves to GeistMono).
- Never import from `next/font` — it's not used in this project.

### Component conventions

- **Primitives** (`Button`, `Input`, `Dialog`, etc.) → install via `npx shadcn@latest add` → live in `components/ui/`.
- **Composed components** (e.g. `UserCard`, `ClassificationGrid`) → hand-written in `components/`. Import from `components/ui/` as needed.
- All components use `cn()` from `@/lib/utils` for className merging — never string concatenation.
- Prefer `"use client"` only at leaf nodes. Keep as much as possible as Server Components.

### Icons

Use `lucide-react` exclusively. Import individual icons by name:
```tsx
import { Upload, Trash2, ChevronRight } from "lucide-react";
```

## Database

### Schema

- One file per domain in `lib/db/schema/` (e.g. `users.ts`, `classifications.ts`).
- Re-export everything from `lib/db/schema/index.ts` — drizzle-kit reads this barrel file.
- Export both `$inferSelect` and `$inferInsert` types from every schema file and re-export them via `types/index.ts`.

### Querying

- Import `db` from `@/lib/db` and table definitions from `@/lib/db/schema`.
- Prefer the relational query API (`db.query.users.findMany`) for joins; use the builder API (`db.select().from(...)`) for aggregations and complex filters.
- All queries return typed results — no `any` casts.

```ts
// Good — lives in lib/, returns a typed result
export async function getUserById(id: string): Promise<User | undefined> {
  return db.query.users.findFirst({ where: eq(users.id, id) });
}
```

### Migrations

Drizzle-kit generates SQL into `lib/db/migrations/sql/` (gitignored). That SQL is reviewed and then run manually in the Supabase SQL Editor. Every migration also gets a hand-written `.md` file in `lib/db/migrations/` documenting:
- What table/column changed and why
- The exact SQL to apply
- A rollback block

The `auth.users` foreign key cannot be expressed in Drizzle's schema builder (cross-schema). It lives only in the migration SQL.

## Authentication

Supabase Auth handles signup, login, and session management. The auth flow:

1. Client calls Supabase Auth (email/password, OAuth, magic link).
2. Session is stored in cookies by `@supabase/ssr`.
3. Server Components read the session via `createSupabaseServerClient()`.
4. A DB trigger (`handle_new_auth_user`) auto-creates a `public.users` row on signup.
5. Middleware (to be added at `middleware.ts`) refreshes the session cookie on every request.

## Storage

**Active: Supabase Storage.** Use the `supabaseAdmin` client (or the server client for user-scoped uploads) to call `supabase.storage.from("bucket").upload(...)`.

**Wired but inactive: Cloudflare R2.** `lib/r2.ts` is fully implemented. The env vars (`R2_*`) are optional in `lib/env.ts`. Enable by filling them in `.env.local` and switching call sites to the R2 helpers.

## Environment variables

Defined and validated in `lib/env.ts` via Zod. The app throws a formatted error at startup if any required variable is missing.

| Variable | Required | Used in |
|---|---|---|
| `DATABASE_URL` | ✅ | `lib/db/index.ts` |
| `SUPABASE_URL` | ✅ | `lib/supabase/admin.ts` |
| `SUPABASE_ANON_KEY` | ✅ | `lib/supabase/admin.ts` |
| `SUPABASE_SERVICE_ROLE_KEY` | ✅ | `lib/supabase/admin.ts` |
| `NEXT_PUBLIC_SUPABASE_URL` | ✅ | `lib/supabase/server.ts`, `lib/supabase/client.ts` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | ✅ | `lib/supabase/server.ts`, `lib/supabase/client.ts` |
| `R2_*` (5 vars) | optional | `lib/r2.ts` |

Copy `.env.local.example` → `.env.local` to get started.

## Development commands

```bash
npm run dev          # Start dev server with Turbopack
npm run build        # Production build
npm run lint         # ESLint

npm run db:generate  # Generate SQL from schema changes (drizzle-kit)
npm run db:studio    # Open Drizzle Studio (visual DB browser)
npm run db:push      # Push schema directly to DB (dev only — use migrations in prod)
```

To add a shadcn/ui component:
```bash
npx shadcn@latest add button
npx shadcn@latest add dialog
```

To regenerate Supabase TypeScript types after schema changes:
```bash
npx supabase gen types typescript --project-id mwrbytebmmdmdkzderlz > types/supabase.ts
```
